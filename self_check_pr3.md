# Самопроверка — практическая работа №3

1. **Merge и rebase.** Merge соединяет истории и сохраняет контекст слияния; rebase переносит коммиты на новую базу и создаёт линейную историю. Rebase подходит для личной незапубликованной ветки, merge — для интеграции совместной работы или когда важна история ветвления.
2. **Почему не rebase публичной ветки?** Он меняет SHA опубликованных коммитов. У коллег остаётся старая история, возникают дубли и конфликты; может понадобиться force-push. Общую ветку переписывают только после явного согласования.
3. **`git rebase -i HEAD~5`.** Открывает план последних пяти коммитов для интерактивного редактирования: `pick` оставить, `reword` изменить сообщение, `edit` остановиться для правки, `squash` объединить с сообщением, `fixup` объединить без сообщения, `drop` удалить коммит из переписываемой истории.
4. **`squash` и `fixup`.** Оба объединяют изменения с предыдущим коммитом; `squash` позволяет отредактировать итоговое сообщение, `fixup` отбрасывает сообщение объединяемого коммита.
5. **Cherry-pick.** Применяет изменение выбранного коммита как новый коммит в текущей ветке. Например, им можно перенести один проверенный hotfix из feature-ветки в `main`, не сливая незавершённые функции.
6. **Восстановление потерянного коммита.** Найти его SHA через `git reflog`, затем создать ветку, например `git switch -c recovered <sha>`, или применить коммит через `git cherry-pick <sha>`.
7. **Revert и reset.** `git revert` создаёт новый коммит, обратный выбранному; история остаётся публичной и непрерывной. `git reset --hard` перемещает указатель и сбрасывает рабочие файлы, поэтому для общей опубликованной ветки безопаснее `revert`.
8. **Второй remote и push в оба.** Добавить его через `git remote add mirror <URL>`. Для двух push-адресов настроить `remote.origin.pushurl` на основной URL и URL зеркала; тогда обычный `git push origin <ветка>` отправляет ветку на оба адреса.
9. **Git hooks.** Это локальные скрипты, запускаемые Git на определённых событиях. Например, `commit-msg` может отклонять сообщения без Conventional Commit-префикса, а `pre-commit` — запускать форматтер или быстрые проверки.
10. **Forking Workflow и GitHub Flow.** В Forking Workflow разработчик работает в собственном fork и отправляет Pull Request в upstream; в GitHub Flow ветки обычно создаются в общем репозитории команды. Forking Workflow особенно удобен в проектах, куда участникам не дают прямой доступ на запись.
