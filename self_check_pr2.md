# Самопроверка — практическая работа №2

1. **Почему нельзя коммитить напрямую в `main`?** Чтобы незавершённое или непроверенное изменение не попало сразу в основную ветку. Feature-ветка и Pull Request дают возможность посмотреть diff, провести ревью и проверить изменения до интеграции.
2. **Шаги GitHub Flow.** Обновить `main`, создать короткоживущую feature-ветку, сделать осмысленные коммиты, отправить ветку на сервер, открыть Pull Request, пройти проверки и ревью, объединить изменения и удалить ветку.
3. **Чем Pull Request отличается от простого merge?** Merge — операция объединения историй. Pull Request — площадка до merge: показывает diff, собирает обсуждение и ревью, запускает проверки и затем позволяет выбрать способ слияния.
4. **Что такое Code Review и зачем он нужен?** Это проверка изменений другим разработчиком до слияния. Она помогает находить дефекты, улучшать читаемость и безопасность кода и делиться знаниями о проекте.
5. **Принципиальная разница между Git и SVN.** Git распределённый: у разработчика есть локальная история и коммиты доступны офлайн. SVN централизован: история и обычный commit зависят от центрального сервера. В современных SVN копирование ветки оптимизировано, но Git удобнее для частого локального ветвления.
6. **Что означает `feat:`?** Тип Conventional Commit, указывающий, что коммит добавляет новую возможность.
7. **Как впервые отправить локальную ветку на GitHub?** Например: `git push -u origin feature/my-change`. Флаг `-u` связывает локальную ветку с одноимённой удалённой.
8. **Зачем DevOps-инженеру Git в терминале?** Терминальные команды воспроизводимы и автоматизируемы, доступны в CI/CD и на удалённых серверах, а также позволяют точно управлять ветками, историей и несколькими remote.
